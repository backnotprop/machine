What we built

You draw the process.
The agent follows it.
A tool keeps it on the rails.

A machine is a set of steps with rules for moving between them. You build it in a UI. The UI outputs a skill file for the agent and a schema. The agent starts a run through a tool. Every step it reports is checked against your rules before it counts. You watch the run live.

The pieces

One definition, three outputs

You only ever edit the definition. Everything else is generated from it, so the map the agent reads and the rules the server enforces can never disagree.

The key idea

The agent never tracks where it is. The tool does.

Instructions alone drift: the model skips a step, invents an event, or declares victory early. So the server owns the run and rejects any move your definition does not allow. The error names what is allowed.

Without rails

The model keeps the process in its head. Nothing stops it from jumping ahead.

# agent, in state "reproduce" "I fixed it, moving on to open the PR" # nothing checks this. Step skipped.
With rails

The same move is rejected. The agent is told which events exist from here.

transition(run, event: "fixed") error: invalid_event event "fixed" is not allowed from state "reproduce". Allowed: reproduced, cannot_reproduce

Wrong event

Not listed on the current state. Rejected.

Bad payload

Missing field, wrong type, value not in the allowed list. Rejected.

Too many loops

"Fix until tests pass" can fire 3 times. The 4th is rejected.

Not your move

Human-only events, or a run that is blocked or finished. Rejected.

What a machine looks like

Example: ship a bug fix

Boxes are states. Arrows are named events. Each state says what to do and what to report when leaving. Dashed arrows can only be fired by a human from the UI.

What one state says

titleRun the full test suite
instructionsRun the whole suite, not just the new test. Report the exact command and result.
must reportcommand text · result pass or fail · failing list (optional)
eventspass → open_pr · fail → fix, at most 3 times

Why "must report" matters

The payload the agent hands over to leave a state is the progress report. The tool checks it is complete and well-typed, and the UI shows it. Pick facts you can see: a PR link, a test command, a count. Not opinions.

Every published edit bumps the version. A run in progress keeps the version it started on.

What the agent actually does

Six moves, repeated

After every move the tool hands back a small state card: just the next instructions, the fields to report, and the events allowed. The agent does not need the whole machine in its head. A new session can pick up with get.

preflightGive the inputs. Get back the list of checks to perform.
checkThe agent runs each check itself and records ok / not ok.
beginSend inputs + check results. Get a run id and the first card.
workDo what the card says. Send notes as progress.
transitionFire one listed event with the report. Get the next card.
stopWhen a card says your_move: false: done, human's turn, or blocked.

A card when it is the agent's move

{ "run_id": "run_o7gwgsjm", "status": "running", "your_move": true, "state": "verify", "instructions": "Run the whole suite…", "output": { command, result: pass|fail, failing? }, "events": [ { name: "pass", to: "open_pr" }, { name: "fail", to: "fix", remaining: 3 } ] }

A card when it is not

{ "run_id": "run_4xk9dqbr", "status": "blocked", "your_move": false, "stop_reason": "Stop. The run is blocked. A human must resolve: a file named .changelog-author holds the preparer's name. Do not try to fix this yourself.", "events": [] } # no instructions, no events. Nothing to do.
"Does the agent have what it needs?"

Three layers, from strict to flexible

Only the agent can answer "is GitHub logged in" or "does the database connect", because it is the one in that environment. So the agent checks, and the server decides whether the run may proceed.

1 · inputs

Checked by the server

Missing or mistyped inputs never produce a run at all.

2 · requirements

Checked by the agent, gated by the server

You list them in the definition with how to check each. A failed required check creates the run as blocked with a to-do list for you.

3 · anything else

The agent calls fail

A code, a plain message, and what a human must provide. Blocked by default so you can fix and unblock. Fatal when it should not continue.

Was it checked?

Yes. Two fresh agents, two repos, no coaching.

Each agent got only the generated skill file and the tool. One repo had everything the machine required. One was missing a file.

✓

collect → draft → self_review → ready. Zero rejected calls. Wrote a correct changelog and explained what it left out.

Missing a file
Reported the failed check. Run created as blocked. Stopped. Did not create the file to sneak past the check.

Their feedback changed the design

A blocked card used to still show instructions and events, which tempted an agent to start working. Now cards carry your_move and a plain stop reason, and show nothing else when it is not the agent's turn. The skill gained the "do not manufacture what a check looks for" rule. Plus 8 automated tests on the engine: wrong events, bad payloads, loop caps, human-only events, version pinning.

Still yours to decide

Open choices

Where runs live

Local files (zero setup) or a hosted server (one UI for every agent and machine).

How much the agent loads

The full skill per machine, or one short generic skill and let the cards carry the rest.

Timeouts

Flip a silent run to blocked after N minutes. Not built.

Notifications

Waiting and blocked runs fit naturally into an inbox you already read.
