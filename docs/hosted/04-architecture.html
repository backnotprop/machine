Hosted machine, how it is put together

Three questions from the thread, answered with pictures: where a hundred companies live, how it grows without falling over, and how an agent uses a stored credential.

1. Every company shares one app

Not one container per customer. One deployment serves all teams; every row in the database carries its team. This is how Basecamp, Linear and GitHub started, and it is what we built.

Is one process enough for a hundred companies? Yes, by a wide margin. The traffic is agents reporting a move every few seconds per run and people watching pages. A run writes once per move: 10,000 runs a day is about 6 writes a second. One small container serves thousands of requests a second.

2. How it grows, and what "falls over" actually means

A single container has exactly three weaknesses. Each has a boring fix, and the fix for the first two is to run a second copy, which is why the database must live outside the app.

Weakness of one containerWhat happensFix
The box diesThe platform restarts it in seconds. Data is safe only if it is not inside the container.Database outside the app (Postgres). With two copies, nobody notices.
A deployA few seconds of downtime while the new version starts.Two copies, rolled one at a time: zero downtime.
More traffic than one boxPages slow down.Add copies behind the load balancer. They share the one database.

→
When needed2–3 copies behind the load balancer, same Postgres
→
Much laterbigger Postgres, read replicas; no redesign

So why not SQLite? SQLite is a file inside the app's own disk. It is fast enough for a big launch, but a second copy of the app cannot share that file, so every one of the fixes above is closed off. Postgres keeps them open. Cost: about a day now, because the engine talks to the store synchronously today. Kubernetes is not needed: Fly.io (or Railway) runs copies of a container and a Postgres for us from a dashboard.

3. The three ways an agent uses a stored credential

The team pastes a token once, on the Credentials page. From then on the agent uses it in one of three ways. All three are built; the question is which one we polish and show.

The lease · recommended

The agent runs the command it already knows, with one prefix:

machine run r_8f2 -- gh pr create

Our CLI fetches the token for the current step, puts it in that one command's environment, runs it, cleans up. The agent never sees the value.

Agent ergonomics: nothing new to learn; gh, npm, aws, git work as always.
Human ergonomics: paste the token once.
Needs: our CLI installed and logged in where the agent runs (a laptop or CI).

The proxy

The agent calls our tool instead of GitHub:

request(credential: "github", method: "POST", path: "/repos/acme/app/pulls", body: …)

Our server adds the auth header and makes the HTTP call.

Agent ergonomics: it must translate every action into raw API calls, by hand, instead of using the CLI it knows. Fine for one call, tedious for a workflow.
Covers: HTTP APIs only, not CLIs.
Works from anywhere, even a sandbox without our CLI.

The plain hand-off · off by default

The agent asks and gets the raw value:

credential(id: "github") → ghp_…

The value is now in the agent's context and transcript. Each use shows red on the run's timeline, and a team must switch it on per credential.

The cases it exists for: the secret has to be written into a file a tool reads (a .env for a deploy, a Terraform variable); a tool logs in on a remote host over ssh where we cannot inject; the agent runs in a hosted sandbox with no machine CLI and the job needs a CLI, not an API.

Simplest end to end: the lease, for both sides. The proxy is the fallback when the agent has no CLI. The hand-off is the escape hatch we would rather never need; keeping it off by default costs nothing and avoids a "we can't do X" the week after launch.
